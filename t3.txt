# Техническое задание: cest

## 1. Цель проекта

Нужно реализовать открытый GitHub-проект `cest`: надёжную и экономную по CPU/RAM утилиту командной строки на Go для получения новых доменных имён из Certificate Transparency (CT) логов.

Утилита должна:

1. следить за актуальными CT-логами из официального списка Google;
2. извлекать DNS-имена из новых сертификатов и precertificate;
3. нормализовать, валидировать, фильтровать и дедуплицировать имена;
4. немедленно публиковать новые имена в WebSocket-маршрут `/all`;
5. опционально, только при наличии хотя бы одного `--stream`, проверять сайты по HTTP/HTTPS и публиковать домены в дополнительные WebSocket-маршруты по найденным в заголовках или теле строкам;
6. предоставлять статистику через HTTP `/stats`;
7. работать в foreground или самостоятельно демонизироваться.

Главные приоритеты в порядке важности:

1. стабильность и отсутствие блокировок всего pipeline из-за одного CT-лога, DNS-сервера, сайта или медленного WebSocket-клиента;
2. минимальное потребление CPU и памяти;
3. bounded-очереди и предсказуемое поведение при перегрузке;
4. простой запуск без конфигурационных файлов и внешних сервисов.

Целевая платформа: актуальные Ubuntu/Debian Linux. Использовать актуальную стабильную версию Go на момент реализации.

## 2. Ограничения и намеренно отсутствующие функции

- Конфигурация задаётся только CLI-флагами. Конфигурационных файлов и переменных окружения нет.
- Состояние между запусками не сохраняется.
- Исторические записи CT не загружаются.
- Checkpoint/STH, consistency proof и inclusion proof криптографически не проверяются.
- Prometheus, structured logging, уровни логов, аутентификация и TLS для встроенного HTTP/WebSocket-сервера не нужны.
- Дополнительные пользовательские CT-логи не поддерживаются.
- DNS-over-TCP, DoT, DoH и DNSSEC не поддерживаются.
- Системный DNS resolver использовать нельзя.
- HTTP keep-alive и connection pooling для сортировщика не использовать.
- Без `--stream` DNS/HTTP pipeline вообще не создаётся и не запускается.

## 3. Источники CT

### 3.1. Каталог логов

Использовать динамический официальный список Google:

`https://www.gstatic.com/ct/log_list/v3/log_list.json`

Поддержать оба типа источников из списка:

- RFC6962 `logs`;
- Static CT `tiled_logs`.

При запуске, если список недоступен, повторять запрос каждые 3 секунды без завершения процесса. После успешного запуска обновлять список раз в 24 часа. Ошибки отдельного обновления не должны останавливать уже работающие workers.

Каждый раз при обновлении списка:

- запускать новые подходящие логи;
- останавливать удалённые, перешедшие в запрещённое состояние или попавшие в denylist логи;
- не создавать второй worker для уже работающего LogID;
- идентифицировать лог прежде всего по `log_id`, URL использовать как дополнительную проверку/fallback.

### 3.2. Разрешённые состояния

Мониторить только логи в активных состояниях `usable` и `qualified`.

Не мониторить:

- `pending`;
- `readonly`;
- `retired`;
- `rejected`;
- лог с отсутствующим или неизвестным состоянием.

### 3.3. Постоянный denylist

Никогда не читать следующие логи, даже если они присутствуют в динамическом списке в разрешённом состоянии:

- Google ParcelYard2026h2;
- Google ParcelYard2027h1;
- DigiCert Sphinx2026h2;
- DigiCert Sphinx2027h1;
- Let's Encrypt Sycamore2026h2;
- Let's Encrypt Sycamore2027h1;
- Let's Encrypt Willow2027h1;
- HARICA Selene2027h1;
- Sectigo Mammoth2026h2;
- Sectigo Sabre2026h2.

Denylist следует хранить в коде по известным LogID. Для устойчивости к изменению каталога дополнительно разрешается fallback-сопоставление по нормализованному URL и точному description. Нельзя исключать будущие шардированные логи только по общему имени семейства: например, запрет `Sphinx2027h1` не запрещает `Sphinx2027h2` или будущий `Sphinx2028h1`.

### 3.4. Старт и восстановление

При каждом запуске и при каждом добавлении нового лога начинать строго с текущего конца:

- RFC6962: получить текущий STH и использовать `tree_size` как next index;
- Static CT: получить текущий checkpoint и использовать его size как next index.

Курсоры на диск не записывать. После рестарта снова начинать с текущего конца. Catch-up и восстановление пропущенных во время остановки записей не нужны.

Внутри живого процесса worker обязан хранить next index, чтобы не повторять уже обработанную запись. При временной ошибке CT-источника повторять запросы с exponential backoff и jitter. Ошибка одного источника не должна влиять на остальные.

## 4. Извлечение доменных имён

### 4.1. Минимальный ASN.1 parser

Не выполнять полный разбор X.509-сертификата и цепочки. Не вычислять fingerprints/hashes, не кодировать сертификаты в base64 и не извлекать ненужные extensions.

Реализовать узкий безопасный ASN.1 DER parser, который извлекает только:

- `dNSName` из Subject Alternative Name;
- legacy Common Name из Subject.

Обрабатывать:

- обычные X.509 log entries;
- precertificate entries, включая defanged TBSCertificate из Static CT tiles;
- сертификаты конечных узлов и CA-сертификаты.

Для CA также извлекать SAN и CN: CA-сертификаты не отбрасывать.

Парсер должен строго проверять DER lengths и границы буфера. Некорректная запись пропускается и учитывается в статистике, но не останавливает worker.

### 4.2. Семантика CN и SAN

- Сначала получить DNS SAN в исходном порядке.
- Добавить CN, если он непустой и ещё не присутствует среди SAN после нормализации.
- Удалить дубликаты внутри одного сертификата.
- Извлекать только DNS-имена. IP SAN, email, URI и другие GeneralName игнорировать.

### 4.3. Нормализация и валидация

Для каждого имени:

1. удалить окружающие ASCII-пробелы;
2. привести к lowercase;
3. удалить завершающую точку;
4. если имя начинается с `*.`, удалить только этот первый префикс;
5. преобразовать Unicode-домен в ASCII IDNA A-label;
6. повторно привести к lowercase и удалить завершающую точку;
7. проверить синтаксис DNS-имени.

Сохранять полный subdomain. Не приводить имя к eTLD+1.

Имя считается корректным, если:

- общая длина не больше 253 ASCII-символов без завершающей точки;
- содержит минимум две labels;
- каждая label имеет длину 1–63;
- label содержит только `a-z`, `0-9`, `-`;
- label не начинается и не заканчивается дефисом;
- TLD не состоит только из цифр;
- строка не является IPv4/IPv6-адресом;
- после удаления wildcard нет других `*` или wildcard-символов.

Некорректные имена отбрасывать и учитывать в `/stats`.

## 5. Фильтрация

### 5.1. Встроенный фильтр

Если не указан `-nf`/`--nofilter`, исключать нормализованные полные доменные имена, соответствующие исходному case-insensitive правилу:

### 5.2. Пользовательский фильтр

`-f`/`--filter REGEX` можно передать максимум один раз. Regex:

- применяется дополнительно к встроенному фильтру;
- всегда case-insensitive;
- ищется в любом месте нормализованного полного домена;
- продолжает применяться при `--nofilter`;
- компилируется при запуске; при ошибке программа выводит понятную ошибку и завершается с ненулевым кодом.

## 6. Глобальная дедупликация

После нормализации/валидации/фильтрации и перед `/all` использовать один общий bounded FIFO-set на 100 000 уникальных доменов:

- если домена в set нет, добавить его в конец и передать дальше;
- если домен уже есть, отбросить его и не менять его позицию;
- при добавлении 100 001-го уникального домена удалить из set самый старый;
- состояние хранить только в памяти;
- TTL нет;
- после вытеснения домен может снова попасть в поток;
- повторная выдача нового сертификата для домена, пока тот есть в set, намеренно скрывается.

Операция должна быть O(1): map + ring/list. Учитывать количество отброшенных дубликатов в `/stats`.

## 7. Публикация `/all`

Каждый прошедший дедупликацию домен немедленно публикуется всем подключённым WebSocket-клиентам маршрута `/all` независимо от наличия `--stream`.

Формат одного логического сообщения — одна строка домена без JSON. Только для маршрута `/all` допускается транспортное batching до 100 доменов в одном WebSocket text frame; в таком frame домены разделяются `\n`, завершающий `\n` разрешён. Клиент `/all` должен трактовать каждую непустую строку как отдельный домен. На всех маршрутах сортировки `/<path>` batching запрещён: один WebSocket text frame должен содержать ровно один домен без `\n`.

Новые клиенты не получают историю, только сообщения после подключения.

## 8. HTTP/HTTPS сортировка

### 8.1. Включение pipeline

DNS и HTTP pipeline создаётся только при наличии хотя бы одного `-s`/`--stream`.

Каждый прошедший глобальную дедупликацию домен:

1. сразу публикуется в `/all`;
2. асинхронно помещается в bounded sort queue;
3. разрешается собственным DNS resolver;
4. проверяется по HTTP, при необходимости один раз по HTTPS;
5. публикуется во все stream routes, чьи case-sensitive literal substring найдены в заголовках или теле успешного ответа; если несколько правил одного path совпали, домен публикуется в этот path только один раз.

Sort queue реализовать как кольцевой буфер (ring buffer) фиксированной ёмкостью `threads * 10`, где `threads` — значение `-t`/`--threads`. Отдельного флага размера sort queue нет.

Переполнение sort queue не должно блокировать CT ingestion: атомарно удалить самый старый ещё не обработанный домен, добавить новый и увеличить монотонный счётчик `sort_queue_dropped`. Этот счётчик отражает общее число вытесненных из sort ring buffer доменов с момента запуска и обязательно публикуется в `/stats`. Операции добавления и извлечения должны иметь O(1), а память под элементы буфера должна выделяться в ограниченном объёме.

### 8.2. Worker pool

`-t`/`--threads N` задаёт максимальное число одновременно работающих sort workers. Значение по умолчанию: 2000.

Это лимит конкурентных доменов, а не требование заранее создавать 2000 активных сетевых соединений. Допустимо создать фиксированный pool из N goroutines, ожидающих bounded queue.

`N` должен быть положительным. Неразумно большое значение, при котором нельзя безопасно создать ресурсы, должно приводить к понятной ошибке при запуске.

### 8.3. DNS перед HTTP

Сначала получить IPv4-адрес домена через встроенный resolver. Использовать любой первый допустимый A-адрес из ответа. Если нет допустимого адреса, домен не проверять.

Запрещать соединения со следующими адресами:

- unspecified;
- loopback;
- private RFC1918;
- link-local;
- multicast;
- carrier-grade NAT `100.64.0.0/10`;
- documentation/test ranges;
- benchmark/reserved/broadcast ranges.

Проверка должна выполняться по фактическому IP, к которому подключается HTTP client. Нельзя после собственной проверки снова резолвить hostname системным resolver. Соединяться напрямую с выбранным IP, но устанавливать:

- HTTP `Host` равным исходному домену;
- TLS `ServerName` равным исходному домену.

### 8.4. HTTP-запрос

Первый запрос:

`GET http://<domain>/`

Требования:

- редиректы не выполнять;
- успешными всегда считать `200 OK` и дополнительные коды, переданные через `-c`/`--code`;
- заголовки и response body проверять только у ответа с успешным status;
- любой неуспешный status считается ошибкой HTTP и приводит к одной попытке HTTPS;
- заголовки и тело неуспешного ответа не сканировать;
- response body читать в распакованном виде максимум до 200 KiB;
- после достижения лимита прекратить чтение и закрыть connection; первые 200 KiB всё равно проверить;
- поддерживать стандартное автоматическое распаковывание gzip; для Brotli добавить поддержку либо явно посылать `Accept-Encoding: gzip` без `br`;
- искать stream strings в названиях/значениях HTTP-заголовков и в теле любого content type;
- поиск чувствителен к регистру и является literal byte substring, не regex;
- один домен может совпасть с несколькими stream rules и должен попасть во все соответствующие маршруты;
- несколько правил с одинаковым path объединяются в один поток: если совпало несколько их строк, домен отправляется в этот path только один раз;
- HTTP keep-alive отключить; после ответа connection закрыть;
- User-Agent — строка стабильного desktop Chrome, актуальная на момент релиза. Хранить её в одной константе, чтобы легко обновлять; динамически загружать UA из сети не нужно.

Если HTTP не вернул успешный status (`200` или код из `--code`) по любой причине — DNS/connect/read timeout, другая сетевая ошибка или неразрешённый status — выполнить ровно одну попытку:

`GET https://<domain>/`

Для HTTPS:

- использовать тот же уже разрешённый и проверенный IPv4, без повторного системного DNS;
- принимать self-signed, просроченные, выпущенные не на этот hostname и иным образом невалидные сертификаты (`InsecureSkipVerify` допустим и намерен);
- при этом передавать TLS SNI исходного домена;
- остальные правила те же;
- если HTTPS также не дал успешный status, сайт считается недоступным для сортировки.

### 8.5. Timeout и лимиты

Значения по умолчанию:

- DNS query timeout: 1 секунда;
- connect timeout: 2 секунды;
- полный срок получения/чтения HTTP response: 5 секунд на одну попытку HTTP или HTTPS;
- body limit: 200 KiB.

Добавить CLI-флаги:

- `--dns-timeout DURATION`;
- `--connect-timeout DURATION`;
- `--response-timeout DURATION`;
- `--body-limit-kb N`.

Duration использовать в Go-формате (`500ms`, `2s`, `1m`). Все значения должны быть положительными.

## 9. Собственный DNS resolver

### 9.1. Общие требования

Не использовать `net.DefaultResolver`, `/etc/resolv.conf`, cgo/system resolver или скрытый повторный hostname lookup внутри HTTP client.

Реализовать минимальный DNS client поверх UDP/53:

- только IPv4 DNS-серверы;
- только A queries;
- random query ID;
- EDNS(0) с advertised UDP payload size 4096;
- безопасный разбор UDP datagram, включая compressed names, большие ответы, несколько answer records и CNAME;
- CNAME-following максимум на 3 перехода;
- DNSSEC не запрашивать/не валидировать;
- TCP fallback не делать.

Хотя полноценная security-валидация DNS не требуется, parser обязан проверять границы буфера, длины labels и compression pointer loops, чтобы malformed packet не вызвал panic или бесконечный цикл. Ответ с несовпадающим transaction ID или не являющийся response на ожидаемый вопрос следует игнорировать — это минимально необходимая корректность UDP resolver.

Если ответ содержит `TC=1`, повторить запрос ровно через один другой DNS-сервер. Если второй ответ также truncated/ошибочен/не получен — считать DNS lookup неуспешным. Обычный timeout/ошибка выбранного сервера также допускает одну повторную попытку через другой сервер.

DNS-кэш не нужен.

### 9.2. Автоматический выбор серверов

Если `--dns` не задан:

- в коде хранить список из 60 уникальных известных публичных IPv4 DNS resolver addresses разных операторов (несколько адресов одного оператора допустимы);
- при старте измерить их доступность и скорость;
- выбрать до 20 лучших по комбинации success rate и RTT;
- использовать выбранные 20 (или меньше при недоступности части серверов) round-robin;
- повторять benchmark раз в час и атомарно заменять рабочий список, не прерывая текущие запросы.

Benchmark выполняется с машины, где запущен `cest`. Чтобы результат был воспроизводимым и проверял реальную рекурсию, использовать небольшой захардкоженный набор из трёх стабильных общедоступных имён, по одному A-запросу на имя для каждого resolver. Score сортируется прежде всего по числу успешных ответов, затем по median RTT. Resolver без успешных ответов не выбирать. Если доступно меньше 20, использовать все доступные. Если не доступен ни один, продолжать benchmark с интервалом 3 секунды; CT `/all` продолжает работать, sort pipeline временно считает DNS lookup неуспешными.

Конкретные три benchmark hostname и список 60 resolver должны быть документированы в README и покрыты unit tests на корректность формата, уникальность адресов и выбор до 20 лучших серверов. Часть публичных resolver применяет security/family/regional-фильтры; это ограничение описать в README, для выбора доверенных resolver пользователь может использовать `--dns`. Нельзя использовать hostname самой машины как DNS question; формулировка «с сервера, где запускаемся» означает место измерения RTT.

### 9.3. Пользовательские DNS

`-dns`/`--dns IP1,IP2,...` полностью заменяет автоматический список.

- разрешены только уникальные IPv4 literals;
- порт всегда 53;
- hostname, IPv6 и пользовательский порт запрещены;
- пустые элементы и некорректный IP являются ошибкой запуска;
- серверы используются round-robin;
- hourly benchmark и автоматическая замена для пользовательского списка не выполняются;
- при retry выбирать другой сервер, если в списке есть минимум два.

## 10. WebSocket и клиентские буферы

### 10.1. Маршруты

Всегда существуют:

- `/all` — полный поток прошедших фильтрацию и глобальную дедупликацию доменов;
- `/stats` — обычный HTTP endpoint, не WebSocket.

Каждый `--stream path:string` создаёт WebSocket route `/<path>`.

`path`:

- не должен быть пустым;
- может содержать только `a-z`, `0-9`, `-`, `_`, `.`;
- не должен начинаться с точки;
- значения `all` и `stats` зарезервированы;
- повторяющиеся path разрешены и объединяются в один WebSocket route; каждое повторение добавляет ещё одну искомую строку.

`string` может быть любой непустой UTF-8 строкой. Разделитель — первый символ `:`; всё после первого `:` относится к искомой строке. Пустая строка является ошибкой.

`-s`/`--stream` можно передавать многократно.

### 10.2. Клиенты и backpressure

На одном route может быть много клиентов. Каждый клиент имеет независимую bounded очередь приблизительным размером 10 MiB по сумме байт доменов и служебного overhead, задаваемым `--client-buffer-mb N`.

Требования:

- медленный клиент никогда не блокирует route, других клиентов, CT ingestion или sort workers;
- при переполнении клиентской очереди удалять самые старые ещё не отправленные домены, пока хватает места для нового;
- connection при переполнении не закрывать;
- увеличить индивидуальный и общий счётчик dropped для route;
- если одно сообщение само больше лимита, отбросить его для этого клиента;
- writer маршрута `/all` может объединять до 100 доменов в один text frame, а writer любого stream-route отправляет ровно один домен в каждом frame;
- новый клиент не получает данные, накопленные до подключения.

WebSocket ping/pong heartbeat не нужен: клиенты только получают домены и не обязаны отправлять Pong или другие сообщения. Read deadline у WebSocket отсутствует; соединение не закрывается из-за молчания клиента. Для TCP-соединений WebSocket включить TCP keepalive: idle 60 секунд, interval 15 секунд, count 4. Эти пробы обрабатывает TCP stack ОС, а не клиентское приложение. Ошибку настройки keepalive логировать, но соединение не закрывать. Перед каждой отправкой WebSocket frame устанавливать write deadline на одну минуту вперёд. При ошибке чтения/записи закрывать только socket данного клиента, освобождать его очередь и завершать его goroutines; route и остальные клиенты продолжают работать. Переполнение очереди не закрывает connection. HTTP keep-alive при опросе доменов по-прежнему отключён.

## 11. HTTP `/stats`

`GET /stats` возвращает `200 OK`, `Content-Type: application/json` и последний подготовленный snapshot счётчиков. Endpoint одновременно является health endpoint: если event loop/server работает, он отвечает 200 даже при временной недоступности CT/DNS.

Внутренние счётчики обновляются сразу при событиях, но JSON snapshot для `/stats` пересобирается фоново **раз в 5 секунд**. Каждый HTTP-запрос `/stats` должен отдавать уже готовый кэшированный snapshot, не обходя активные логи, клиентов и очереди и не выполняя тяжёлую агрегацию. Первый snapshot создать при запуске сервера; его возраст не должен превышать примерно 5 секунд в нормальном режиме. В JSON добавить поле `snapshot_unix` с Unix timestamp времени формирования snapshot.

Минимальная JSON-структура:

```json
{
  "snapshot_unix": 1792035600,
  "uptime_seconds": 123,
  "ct": {
    "active_logs": 12,
    "entries": 1000,
    "parse_errors": 2,
    "source_errors": 4
  },
  "domains": {
    "extracted": 3000,
    "invalid": 5,
    "builtin_filtered": 100,
    "custom_filtered": 10,
    "duplicates": 1200,
    "published_all": 1685
  },
  "dns": {
    "queries": 1000,
    "errors": 20,
    "timeouts": 15,
    "truncated": 2,
    "private_address_drops": 3
  },
  "http": {
    "http_200": 500,
    "https_200": 100,
    "http_additional_code_success": 20,
    "https_additional_code_success": 5,
    "non_success_status": 300,
    "connect_errors": 50,
    "read_timeouts": 20,
    "body_limit_hits": 10
  },
  "queues": {
    "sort_length": 10,
    "sort_capacity": 4000,
    "sort_queue_dropped": 3
  },
  "routes": {
    "all": {"clients": 2, "published": 1685, "client_dropped": 4},
    "wp": {"clients": 1, "published": 50, "client_dropped": 0}
  }
}
```

Счётчики монотонны с момента старта и хранятся в `uint64` atomics либо безопасном эквиваленте. `sort_queue_dropped` увеличивается на единицу при каждом вытеснении старейшего домена из sort ring buffer. Не требуется строго транзакционно согласованный snapshot. Можно добавлять дополнительные полезные поля, не удаляя перечисленные.

`non_success_status` считать для каждой фактической HTTP/HTTPS попытки, вернувшей status, которого нет среди `200` и `--code`. DNS error не является `non_success_status`. Успешные дополнительные коды отдельно учитывать в `http_additional_code_success` и `https_additional_code_success`. Отдельно учитывать timeout и сетевые ошибки.

## 12. Встроенный HTTP-сервер

По умолчанию слушать `127.0.0.1:4949`.

- `-p`/`--port N` меняет порт;
- `-expose`/`--expose` меняет bind address на `0.0.0.0`;
- IPv6 listener не нужен;
- TLS не нужен;
- authentication, Origin restrictions, rate limits и лимиты клиентов не нужны.

При ошибке bind программа завершается с ненулевым кодом.

## 13. CLI

Поддержать следующие флаги и aliases:

```text
-nf, --nofilter                 отключить только встроенный фильтр
-f,  --filter REGEX             один дополнительный case-insensitive regex
-p,  --port PORT                HTTP/WebSocket port, default 4949
-s,  --stream path:string       repeatable stream rule; одинаковые path объединяются
-c,  --code CODE,CODE           дополнительные успешные HTTP-коды (например 303,404)

Неизвестный флаг, повторение single-use флага, некорректное число, HTTP-код, regex, DNS IP или stream rule — понятная ошибка и ненулевой exit code.

## 14. Self-daemonization

Без `--daemon` процесс работает в foreground и пишет текстовые диагностические сообщения в stderr.

С `-d`/`--daemon`:

1. parent запускает копию текущего executable с теми же аргументами, удалив `--daemon`/`-d` и добавив внутренний защищённый marker;
2. child создаёт новую session (`setsid`), меняет рабочую директорию на `/`, устанавливает `umask 027`;
3. stdin перенаправляется из `/dev/null`;
4. stdout/stderr перенаправляются в `/dev/null`;
5. parent завершается с кодом 0 только после подтверждения, что child успешно прошёл CLI validation, bind HTTP port и первичную инициализацию; при ошибке возвращает ненулевой код;
6. не допускать рекурсивной демонизации.

PID-файл не нужен. Для production README всё равно должен рекомендовать supervision через systemd, но systemd unit создавать не требуется.

### 14.1. Автоматический Linux tuning

После разбора CLI и, в daemon mode, только внутри рабочего child-процесса выполнить независимые best-effort попытки:

```text
[fd] ulimit -n 524287
[tcp] net.ipv4.ip_local_port_range=1024 65535
[tcp] net.ipv4.tcp_tw_reuse=1
[tcp] net.ipv4.tcp_fin_timeout=2
```

- `RLIMIT_NOFILE` меняется только для текущего процесса через `setrlimit`.
- sysctl меняются через соответствующие `/proc/sys/net/ipv4/*` и являются глобальными для Linux host/network namespace.
- Настройка применяется только если хватает прав; отсутствие прав, read-only `/proc` или низкий hard limit не останавливают запуск.
- Каждая настройка независима и выводит `(ok)` либо `(skipped: причина)`.
- На non-Linux вывести одно сообщение о неподдерживаемой настройке и продолжить запуск.

## 15. Завершение

Обрабатывать `SIGINT` и `SIGTERM`:

1. прекратить приём новых HTTP/WebSocket connections;
2. отменить CT workers и hourly/daily background jobs;
3. перестать принимать новые sort tasks;
4. дать текущим HTTP tasks и WebSocket writers ограниченное время завершиться;
5. закрыть оставшиеся connections;
6. завершить процесс без сохранения состояния.

Graceful shutdown deadline: 10 секунд. Повторный сигнал завершает процесс немедленно.

## 16. Конкурентность и bounded memory

Все очереди должны быть bounded. Запрещены неограниченно растущие slices/maps/каналы, кроме фиксированного набора статистических ключей и списка активных клиентов.

Обязательные границы:

- глобальная дедупликация: 100 000 доменов;
- sort queue: ring buffer ёмкостью `threads * 10`;
- client queue: `--client-buffer-mb`, отдельно на клиента;
- HTTP body: `--body-limit-kb`;
- DNS packet: не больше UDP datagram/EDNS buffer;
- CT fetching: bounded batches и bounded каналы между workers и domain pipeline.

Для внутренней очереди CT → domain pipeline выбрать разумный фиксированный default и реализовать backpressure к конкретным CT workers. Нельзя silently терять CT entries до глобальной дедупликации. Один CT worker не должен удерживать глобальную блокировку во время сети или отправки клиенту.

## 17. Безопасность malformed input

Все внешние данные недоверенные. Обязательны:

- строгие bounds checks в CT tile, TLS serialization, ASN.1 DER и DNS parsers;
- отсутствие panic на malformed input;
- ограничение allocations на длинах, пришедших из сети;
- защита DNS compression pointer loops;
- запрет HTTP connections на локальные/reserved IPv4;
- прямое соединение с уже проверенным IP без повторного системного DNS;
- fuzz/unit tests для parsers желательны, даже если полноценный CI не требуется.

## 18. Логирование

Текстовые сообщения в stderr, без JSON и уровней. Логировать:

- старт и итоговую конфигурацию без лишнего шума;
- добавление/удаление CT worker;
- длительную недоступность CT source с rate limiting;
- изменения автоматически выбранного DNS pool;
- старт/остановку сервера;
- итоговую краткую статистику при graceful shutdown.

Не логировать каждый домен, каждый DNS lookup или каждый HTTP status: это создаёт лишнюю нагрузку.

## 19. Структура проекта и качество реализации

Проект должен быть обычным Go module с понятным разделением как минимум на пакеты:

- CLI/config validation;
- CT catalog и workers;
- minimal ASN.1/domain extraction;
- normalization/filter/dedup;
- DNS client/pool;
- HTTP sorter;
- WebSocket hub/client queues;
- stats/server.

Предпочитать стандартную библиотеку. Допустимы небольшие зрелые зависимости для:

## 21. Критерии готовности

Реализация считается готовой, если:

1. успешно собирается актуальным Go на Ubuntu/Debian;
2. при старте получает динамический Google log list и запускает только разрешённые не-denylisted логи;
3. начинает каждый лог с текущего конца и не создаёт disk state;
4. извлекает SAN/CN из cert и precert узким parser без полного X.509 enrichment;
5. корректно нормализует wildcard, lowercase, trailing dot и IDNA;
6. отбрасывает malformed domains и дубликаты внутри сертификата;
7. встроенный и пользовательский фильтры работают в заданном порядке;
8. FIFO-set на 100 000 записей имеет O(1) операции и заданную семантику повторов;
9. `/all` выдаёт только новые домены после подключения;
10. без `--stream` DNS/HTTP pipeline отсутствует;
11. с `--stream` собственный UDP resolver и HTTP→HTTPS fallback соблюдают timeout/лимиты;
12. HTTP client физически соединяется с проверенным публичным IPv4, не делает системный re-resolve и не следует redirect;
13. несколько клиентов не блокируют друг друга; старые данные вытесняются при переполнении;
14. `/stats` показывает указанные ошибки, drops, очереди и клиентов;
15. обновление CT списка раз в сутки и DNS pool раз в час происходит без остановки pipeline;
16. SIGINT/SIGTERM дают graceful shutdown;
17. `--daemon` не рекурсивен и сообщает parent об ошибке инициализации;
18. malformed ASN.1/DNS/CT input не приводит к panic;
19. проект содержит unit tests для domain normalization/filter/dedup, ASN.1 cert+precert extraction, DNS compression/CNAME/truncation, HTTP fallback/body limit, WebSocket queue eviction и CLI validation.
